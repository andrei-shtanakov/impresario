# Friction log — Stage 4 pilot (M1)

Наблюдения первого боевого прогона `Idea → AxisAssessment → RankedBacklog`
(2026-08-12, RUN-001 оценка + RUN-002 материализация). Формат: трение →
что сделали → что остаётся.

## 1. В contracts v1 не было контракта run record

Guide требовал «записать immutable run/audit record», но объект не был
законтрактован — валидатор упал бы на неизвестном документе в bundle.
**Сделано:** девятый контракт `run-record/v1` (+fixtures).
**Остаётся:** ретроспективно это дыра M0-состава: перечень контрактов
выводился из списка объектов, а не из перечня записываемых артефактов.

## 2. Пространство RUN-id делят два вида прогонов

Assessments несут `run_id` оценочного прогона (RUN-001), материализация
пишет свой run record — наивный `next_id` по каталогу runs/ выдал бы
коллизию RUN-001.
**Сделано:** генератор сканирует и runs/, и run_id всех assessments.
**Остаётся:** в M2 стоит развести типы прогонов явно (evaluation run как
самостоятельная запись).

## 3. Определение типа документа по уникальному полю хрупко к порядку

`run_id` есть и у assessment, и у run record — детект обязан проверять
`assessment_id` раньше `run_id`. Работает, но это неявная зависимость.
**Остаётся:** кандидат на явное поле `contract:` в v2.

## 4. Запись статуса в карточку — только точечной правкой строки

YAML round-trip терял бы комментарии и порядок ключей (урок ruamel из
экосистемы). `select` правит ровно одну строку `status:`; тест фиксирует
побайтовую сохранность остального.

## 5. Оценки авторились LLM вручную, без промпт-харнесса

`prompt_version: prioritizer/manual-v0` — честная метка: воспроизводимого
промпта нет, есть только материализованные оценки с уликами. Детерминизм
гарантирован от нормализованных assessments вниз (P-07), не от идеи вверх.
**Остаётся:** M2 — промпт-харнесс оценщика с фиксированным prompt_version.

**Закрыто (prioritizer) 2026-08-16:** харнесс render+ingest, prompt_version
`prioritizer/v1`; см. спеку 2026-08-16-prioritizer-prompt-harness-design.md.
Живой RUN-003 — за человеком.

## 6. Ось fit_market для внутренних инструментов бедна на улики

«Рынок» внутреннего инструмента = измеренный внутренний спрос, а таких
замеров почти нет: IDEA-105 ушла в pending_unknown, две идеи получили
низкие баллы из-за отсутствия зафиксированной боли, а не её отсутствия.
**Остаётся:** завести дешёвый способ фиксировать внутренний спрос
(частота прогонов, жалобы, время ожидания) до следующего пересчёта.

## 7. Что отработало как задумано

- Тройная ничья 3.33 (IDEA-102/103/104) разрешилась документированным
  нейтральным tie-break по id — без скрытых критериев.
- CAS-семантика: правка карточки после оценки даёт `STALE_INPUT`, чужая
  версия — `VERSION_CONFLICT`; ничего не пишется частично.
- Собственные выходы (backlog, run record, decision) проходят те же
  контракты, что и входы — fail-closed покрывает сам прибор.

## 8. QG-4 прошёл без трения

Select IDEA-101 (2026-08-12, actor andrei): свежесть карточки доказана по
run record, GD-001 + backlog v2 + карточка записаны атомарно под локом с
пре-флайтом. Единственная процедурная особенность: решение принято в чате
и исполнено командой от имени человека — для мультиактороного будущего
нужен способ, чтобы команду запускал сам decision-maker.

## 9. (M2) Идемпотентность «по последней ссылке» — ловушка double-apply

Первая версия `_apply_delta` считала дельту применённой, если
`refs.latest_concept_draft == cd_ref`. Resume из середины цикла
переприменял РАННИЕ дельты (их CD уже не «latest») — двойной бамп версии
и дубли в delta_log. Поймано crash/resume-тестом с побайтовым сравнением.
**Правило:** применённость — по журналу применений (delta_log), не по
«последнему указателю».

## 10. (M2) Два YAML-парсера — два типа для одного timestamp

`yaml.safe_load` в ScriptedAgent парсил `produced_at` в `datetime`, тогда
как контрактный loader держит строки — валидный по содержанию артефакт
падал на schema. Один parse-путь (`parse_yaml_plain`) для всего, что
попадает в модель данных контрактов.

## 11. (M2) `failed` терминален — и это заострило вопрос recovery

Транзиентная ошибка (п.10) записала `failed` в state; повторный запуск
честно отвечал «failed», починка потребовала пересоздания workspace.
Для reference-раннера это приемлемо (fail-closed), но исполняемый бэкенд
(M3/Kapelle) должен различать terminal-verdict и retryable-инфраструктуру.

## 12. (M2) needs_human получил типизированный resume-путь

Развязка PP-101 показала: возобновление после needs_human было ручной
правкой loop.state. Добавлен `forconcept resume` — человеческий акт с
actor/reason, trace-событием и обязательным расширением бюджета итераций;
`failed` остаётся терминальным (fail-closed). Резюмируемость — свойство
только того вердикта, который по смыслу ждёт человека.

## 13. (QG-5) GD-идентификаторы уникальны только в пределах workspace

`next_id` для GateDecision считает существующие ID внутри одного
workspace, поэтому в экосистеме пилота теперь два `GD-001`
(QG-4 select в `pilot/decisions/` и Gate A в
`pilot/forconcept/pp-101/decisions/`). Внутри одного bundle коллизий нет,
но глобальная уникальность решений — кандидат на правку (namespace по
subject или сквозной счётчик) до multi-proposal эксплуатации.

## 14. (QG-5) Гейты прошли без трения

Gate A → readiness (blocked до Gate A, ok после — вычислен честно) →
Gate B → approved: три команды человека, evidence полный, валидатор
подтверждает цепочку теми же независимыми проверками (FSM_EVIDENCE,
GATE_ORDER), которыми ловил бы подделку.

## 15. (QG-5) Плейсхолдер из примера команды стал immutable evidence

Примеры gate-команд содержали `--reason "<...>"`; исполненные копипастой,
они записали плейсхолдеры в оба решения QG-5. Поймано ревью до мержа;
исправлено подтверждёнными формулировками владельца (записи ещё не были
каноном). **Правила:** (а) `gate decide` теперь отклоняет reason вида
`<...>`/пустой с `USAGE`; (б) примеры команд в доках/PR — либо
исполняемые как есть, либо явно неисполняемые.

## 16. (Стадия 6) approved-решение опиралось на устаревшее evidence

Human-развязка needs_human («exempt = prograph-vault») цитировала запись
от 2026-07-26 и не учла отменяющее решение от 2026-07-30 (коммит
`397c865` robin-runtime: план-файл vault — поверхность приёмки
обязательств по ADR-ECO-006). Обнаружено на стадии 6 при чтении целевого
кода; владелец скорректировал решение: канонический реестр пуст.

**Что удержало систему:** (а) approved scope PP-101 — механизмы
(fail-loud, канонический реестр, постоянное раскрытие), а не значение
списка, поэтому перепрохождение гейтов не потребовалось; (б) стадия 6 =
первый момент, когда реализация читает целевой код, — конфликт всплыл
до какого-либо ущерба. **Урок для M2-харнесса:** researcher должен
проверять актуальность цитируемого evidence (искать более поздние
отменяющие записи), а не останавливаться на первом подтверждающем
источнике — RP-501/503 прошли бы этот тест только случайно.

## 17. (M3) Tear «артефакт есть, журнальной записи нет» → терминальный failed

Kapelle пишет артефакт стадии и его exchange-запись двумя транзакциями;
crash-parity тест немедленно вскрыл: crash между ними давал
`chain_violation` → **терминальный** `failed` — восстановимое
инфраструктурное состояние превращалось в terminal verdict, ровно
сценарий friction №11. Reference runner эту границу лечит (crash-тест
доказал байт-равенство), kapelle расходился с oracle.
**Сделано:** heal производной записи из авторитетного артефакта
(kapelle PR #23). **Урок:** предсказание №11 подтвердилось буквально;
crash-parity — самый доходный кейс матрицы: один тест, три дефекта.

## 18. (M3) Гонка хилеров на wall-clock timestamp

Два конкурентных репаира (воркер + фоновый sweep) строили логически
идентичные записи с разными `at` → байтовый `artifact_conflict` → ложный
терминальный `failed` — тот самый исход, который heal должен был
предотвращать. **Сделано:** семантическое разрешение конфликта —
равенство по всем полям, кроме `at`, значит already-done (kapelle
PR #23). **Урок:** производная запись с недетерминированным полем не
может сравниваться байтами; конфликт-детект должен быть доменным.

## 19. (M3) Heal не должен ухудшать порченый store

Append-only heal на порченом логе (поздняя запись есть, ранняя
пропущена) коммитил новую — всё ещё сломанную — ревизию до того, как
View падал fail-closed. Нашёл Copilot на ревью kapelle PR #23.
**Сделано:** guard «писать только когда запись восстанавливает валидную
цепь», иначе no-write и честный отказ. **Урок:** у починки то же
правило validate-then-write, что у обычной записи; «лечение», которое
может навредить, — не fail-closed.

## 20. (M3) Невидимый tear: нет правила — нет отказа

Evaluate/apply-tear (proposal записан, orchestration-запись потеряна)
был структурно невидим для View — ни одно chain-правило не срабатывало,
цикл молча завершался с неполным журналом. Нашло ревью (не тест!) при
приёмке TASK-106; закрыт в TASK-107: heal + View-правило
`missing_orchestration_entry`, скоуп которого точно совпадает с условием
отказа heal'а. **Урок:** fail-closed существует только там, где есть
правило; молчаливая неполнота — худший класс дефекта, и её ищут
ревью и parity по хэшам, а не позитивные тесты.

## 21. (M3, контур) Per-task бюджет-кэп дважды срезал ревью

TASK-106 ($5.37 при кэпе $1.82) и TASK-107 ($5.35 при кэпе $5.00):
задача завершалась, но review-вызов — последний в пайплайне — оба раза
не стартовал. Замещающее ревью вне контура находило Critical'ы
(№18-20 — его улов), то есть срезалась самая ценная стадия.
**Сделано:** замещающее ревью как процесс-заплатка; кэп второй задачи
подняли — не хватило $0.35. **Остаётся (handoff spec-runner):** у CLI
уже есть `--reserve review=USD` — включить в конфиг kapelle;
наш урок: кэп задачи = оценка работы + ревью + запас, а стоимость
задач класса TASK-106/107 стабильна (~$5.4).

## 22. (RUN-003) Исполнитель перепутал пары brief↔answer — харнесс не мог это поймать

Первый живой прогон харнесса prioritizer/v1: исполнитель (LLM-оценщик)
сопоставил answers с briefs по предположенному порядку render-отчёта и
перепутал пары IDEA-106/IDEA-108. Все typed-проверки прошли — answer
намеренно не несёт identity, связь пар лежит на исполнителе by design.
Поймано только ручной пост-ingest сверкой idea_ref ↔ содержание
rationale; исправлено до коммита (run не был материализован в evidence).
**Урок:** пост-ingest сверка mapping'а — обязательный шаг исполнителя;
структурно проблему закроет envelope с brief_ref (заполняется
исполнителем), уже записанный в спеке как расширение для async-бэкенда —
этот инцидент повышает его приоритет.
